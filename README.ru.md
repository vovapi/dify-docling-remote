# Docling Remote для Dify

Лёгкий плагин Dify для отдельно развёрнутого **Docling Serve**. Конвертация, OCR, извлечение таблиц и разбиение на фрагменты выполняются на вашем сервере. Плагин не устанавливает Docling, Torch или модели.

[English](README.md) · [Релизы](https://github.com/vovapi/dify-docling-remote/releases) · [Конфиденциальность](PRIVACY.md)

## Установка

1. Разверните Docling Serve отдельно, подготовьте модели и языки OCR. Проверенная версия — **Serve 1.21.0**. См. [инструкцию сервера](https://github.com/docling-project/docling-serve) и проверенные [ограничения зависимостей](https://github.com/vovapi/dify-docling-remote/blob/v0.1.4/docs/serve-requirements.txt).
2. Скачайте `docling-remote-0.1.4.difypkg` из [релиза v0.1.4](https://github.com/vovapi/dify-docling-remote/releases/tag/v0.1.4) и установите через Dify → Plugins → Install from local package, соблюдая политику администратора для частных плагинов.
3. В настройках провайдера задайте **Docling Serve URL**, например `http://docling-serve:5001`, без `/v1`. При необходимости укажите API-ключ, соответствующий `DOCLING_SERVE_API_KEY` сервера.
4. Выполните **Server health**, добавьте **Convert documents** в workflow и подключите загруженные файлы к входу Documents.

Среда плагина — Python 3.12. В Docker `localhost` означает контейнер плагина: подключите Serve и plugin daemon к общей сети либо используйте шлюз хоста. [Пример Compose](https://github.com/vovapi/dify-docling-remote/blob/v0.1.4/compose.yaml) предоставлен без интеграционной проверки. Для доступа из Dify Cloud к частному серверу нужен отдельно настроенный сетевой маршрут. В недоверенных сетях используйте HTTPS.

## Использование и ограничения

- От 1 до 10 непустых файлов, каждый не более 50 МиБ. Все входные файлы скачиваются перед конвертацией, чтобы ссылки не истекали во время долгой обработки.
- Экспорт: Markdown, Docling JSON, HTML, текст и DocTags. Выходы: `text`, структурированный `json` и ZIP в `files`.
- Языки OCR, стандартный/VLM pipeline, обогащение и hierarchical/hybrid chunking зависят от моделей сервера. Для chunking используется готовый Docling JSON без повторного OCR.
- PDF backend по умолчанию — `pypdfium2`: в проверенной связке Serve 1.21.0 / Jobkit 1.24.0 стандартный `docling_parse` завершался ошибкой. Другой backend требует совместимых серверных зависимостей.
- Тайм-аут на документ — 600 секунд по умолчанию, диапазон 10–7000. Лимит workflow Dify должен покрывать весь пакет. Тайм-аут не отменяет серверную задачу; автоматических повторов нет.
- Каждый JSON-ответ и суммарные исходные результаты ограничены 100 МиБ. В смешанном пакете сохраняются ошибки отдельных документов; при отказе всех документов возникает ошибка. Статус `partial_success` сохраняется и может требовать проверки содержимого.

Полные экспорты и встроенные изображения остаются в ZIP. Из inline JSON удаляются встроенные изображения; его размер ограничен 2 МиБ с учётом Unicode-экранирования. Для больших результатов сохраняется Markdown каждого файла, если он помещается. Иначе `inline_text_omitted` отмечает пропуск текста, а `full_result_in_zip` указывает путь в архиве. Общий текст ограничен 256 тысячами символов с явным уведомлением об обрезке. Следующие узлы анализа должны проверять эти признаки.

[examples/workflow_texts.py](https://github.com/vovapi/dify-docling-remote/blob/v0.1.4/examples/workflow_texts.py) — адаптер для узла Code в Dify: свяжите `docling_json` и `docling_text` с выходами инструмента. Он возвращает `texts` и `files_count`, принимает непустые частичные результаты и отклоняет ошибки документов или пропущенный текст. При отсутствии структурированных результатов отклоняет обрезанный общий текст.

## Совместимость

Ранее проверены Dify 1.17.1, нативная среда плагина Linux arm64 и Docling Serve 1.21.0: многоязычный HTML, сканированные PDF, экспорты, hierarchical chunking и пакетная конвертация. Успешная конвертация не гарантирует точность OCR. CUDA, VLM/обогащение, Dify Cloud, среда amd64 и работа под полной нагрузкой не проверены. Одобрение Marketplace не заявляется.

## Разработка

```sh
uv sync --frozen
uv run pytest -q
uv run python scripts/package.py --cli /path/to/dify
```

Нужны Python 3.12 и официальный Dify CLI. Сборка использует явный список разрешённых runtime-файлов и сохраняет пакет с `SHA256SUMS` в игнорируемый `dist/`. CI запускает тесты и сверяет `requirements.txt` с `uv.lock`; зависимости обновляйте вместе.

Для необязательной проверки с реальным сервером задайте `DOCLING_TEST_URL`, `DOCLING_TEST_API_KEY` и выполните `uv run python -m scripts.integration`. Дополнительный `DOCLING_TEST_SCAN` задаёт путь к локальному скану с текстом `12345`. Ключи, документы, окружения и модели не должны попадать в Git.

## Конфиденциальность и поддержка

Документы и имена файлов передаются в Serve, выбранный администратором. Входы workflow не могут изменить URL сервера. Перенаправления и прокси из окружения отключены, проверка TLS включена. Исходные тела серверных ошибок и учётные данные не раскрываются в диагностике клиента. Хранение данных в Dify и Serve контролирует администратор. Подробнее — [PRIVACY.md](PRIVACY.md).
